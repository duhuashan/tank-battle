## 3. 核心概念

### 3.1 先加一个状态变量

代码里现在只有 `running`（程序开着吗）。再加一个：

```python
# 游戏状态：playing = 正在玩，over = 结算画面
game_state = "playing"
result_title = ""   # 结算画面的大标题
result_sub = ""     # 结算画面的说明文字
```

名字用**字符串**还是 **0/1** 都行，字符串的好处是调试时 `print(game_state)` 一眼就懂。三个变量都放在 `score` / `lives` 旁边。

**为什么需要它**：主循环里要问好几次"现在是玩还是结算"（更新要不要跑？结算画面要不要画？按 `R` 要不要理？）。拿一个变量统一回答，别用 `lives <= 0 or not enemies` 到处重复判断 —— 那种写法在你按 `R` 之后会自动"复活"成 playing，再想加个"暂停"功能就没地方放了。

### 3.2 ⭐ 地图必须存档，而且必须**深一层**拷贝

这是本条的核心难点，也是 Issue #3 的正式还款。

**问题**：`MAP_DATA` 不是只读的地图配置，它是**可变游戏状态** —— 条目 8 的 `Bullet.hit_wall()` 里那句 `MAP_DATA[row][col] = 0` 已经把打掉的砖墙**永久抹掉了**。你重开一局时如果只重置分数和敌人，**上一局打烂的墙会留着**：玩家出生在一片废墟里。

**第一个错误想法**：`MAP_BACKUP = MAP_DATA`。这只起了个别名，两个名字指向**同一个列表**，改哪个都一样 —— 实测：

```
[PASS] A8 [反例] 直接赋值只是起别名，改谁都一样
```

**第二个错误想法**：`MAP_BACKUP = [row for row in MAP_DATA]`。这看着像拷贝了，其实只拷了**外层** —— 每一行还是**同一个行对象**。实测：

```
[PASS] A7 [反例] 浅拷贝当存档会被连带改掉，等于没存
       BAD1[2][2]=0（0 = 被连带改了）
```

**正确写法**（内外两层都拷）：

```python
MAP_BACKUP = [row[:] for row in MAP_DATA]   # 初始地图存档
```

`row[:]` 是"把这一行复制成新的一行"，外面的 `[... for row in ...]` 是"把每行装进一个新列表"。里外都新，才和原表彻底分家。实测：

```
[PASS] A2 存档与 MAP_DATA 不共享行对象（深一层拷贝）
[PASS] A4 存档未被污染（这正是深拷贝的意义）
```

位置：紧跟在 `MAP_DATA` 定义之后（也就是 `MAP_ROWS = len(MAP_DATA)` 前面）。

**恢复时怎么写**：

```python
MAP_DATA[:] = [row[:] for row in MAP_BACKUP]
```

`MAP_DATA[:] = ...` 是**切片赋值**：它把右边的内容**塞进原来那个列表**里，而不是让 `MAP_DATA` 这个名字改指向新列表。

> **这一步很关键，别偷懒写成 `MAP_DATA = [...]`**：`MAP_DATA` 这个名字一旦改指向新列表，别处**早就拿到的引用**就还指着旧列表（比如你在探针里、或者以后拆模块时，某个函数把 `MAP_DATA` 存进了自己的变量）。切片赋值保证**全世界看到的还是同一个列表对象**。实测：
>
> ```
> [PASS] A6 还原后仍是同一个 MAP_DATA 对象（别的函数引用不失效）  id 不变
> ```

### 3.3 切片赋值还有个好性质：不需要 `global`

`reset_game()` 里要改 `score`、`lives`、`tank`、`enemies` 这些模块级变量，**必须写 `global`**。但 `MAP_DATA` 是个例外：

```python
MAP_DATA[:] = [row[:] for row in MAP_BACKUP]   # ← 这行不用 global
```

**理由**：`global` 只管"**给名字重新赋值**"这件事。`MAP_DATA[:] = ...` 从头到尾**没有给 `MAP_DATA` 赋值**，只是调用了这个列表的方法（等价于 `MAP_DATA.__setitem__(slice(...), ...)`）。所以 Python 认为这跟"读"没区别，不触发局部变量规则。

实测（在真实 main.py 的命名空间里跑）：

```
[PASS] A5 切片赋值还原成功  64 -> 67
[PASS] A6 还原后仍是同一个 MAP_DATA 对象
```

> ⚠️ **但别把这个"例外"推广**：`reset_game` 里 `score = 0`、`tank = Tank(...)` 这些**是重新赋值**，漏写 `global` 会**静默失效**——函数跑完什么都不变，还不报错。第二种情况更坑：
>
> ```
> [PASS] B（实测）先读后写的重绑定：
>   UnboundLocalError: cannot access local variable 'X' where it is not associated with a value
> ```
>
> **规则**：函数里只要**写**了某个全局变量（`x = ...` / `x += ...`），就在函数开头 `global` 把它列上。只读的（比如 `draw_hud` 读 `score`）不用写。

### 3.4 结算画面 = 一层半透明黑 + 几行字

**半透明遮罩**：想让底下的战场"变暗但还看得见"，需要一张盖满屏幕的黑 Surface，并给它设透明度：

```python
OVERLAY = pygame.Surface((SCREEN_WIDTH, SCREEN_HEIGHT))
OVERLAY.fill((0, 0, 0))
OVERLAY.set_alpha(170)     # 0 = 全透明，255 = 全黑。170 大约留三成亮度
```

**两个硬性要求**：

1. **必须在 `pygame.display.set_mode()` 之后创建** —— 否则报 `error: No convert format has been set, try display.set_mode() or Window.get_surface().`
2. **同一帧只贴一次** —— `set_alpha` 是"这张图以多少透明度贴出去"，不是"贴上去之后越来越黑"。但你**连贴多次就会越来越黑**，实测：

   ```
   [PASS] C 同一张半透明遮罩连贴 4 次 → Color(15,0,0,255)，越贴越黑
   ```

   正常写法里 `draw_result()` 每帧被调用一次、里面 `blit` 一次，不会踩到；但如果你以后写"渐暗动画"（多贴几次做出淡入效果），要记住这个行为。

**画字**（沿用条目 12 的三步走，`HUD_FONT` 已存在，本条再加两个大号字体）：

```python
def draw_result(surface):
    """结算画面：遮罩 + 标题 + 说明 + 最终得分 + 重开提示"""
    surface.blit(OVERLAY, (0, 0))
    for font, text, cy in [
        (TITLE_FONT, result_title, 240),
        (INFO_FONT, result_sub, 330),
        (INFO_FONT, f"最终得分  {score}", 385),
        (INFO_FONT, "按 R 重新开始", 460),
    ]:
        surf = font.render(text, True, HUD_COLOR)
        surface.blit(surf, surf.get_rect(center=(SCREEN_WIDTH // 2, cy)))
```

`get_rect(center=(400, cy))` 是条目 12 学的锚点技巧的另一半：`topright=` 用来靠右对齐，`center=` 用来**水平居中**。写死 `(300, 240)` 的话，换个字符串就不居中了。

**实测字号**（simhei，`SDL_VIDEODRIVER=dummy` 之外的真实渲染尺寸，供你对照）：

| 字符串 | 字号 | 渲染出的尺寸 (宽×高) |
|---|---|---|
| `游戏结束` | 64 | 256 × 64 |
| `胜利！` | 64 | 192 × 64 |
| `生命耗尽` | 32 | 128 × 32 |
| `敌人已全部消灭` | 32 | 224 × 32 |
| `最终得分  300` | 32 | 208 × 32 |
| `按 R 重新开始` | 32 | 208 × 32 |

**字号选择**：标题 64、正文 32。窗口高 600，四行分别放在 y = 240 / 330 / 385 / 460，上下留白均匀、四行之间不打架（最宽的一行 256px，离左右各留 272px）。

### 3.5 结算之后，世界必须停下来

**最容易漏的一条**。如果你只是"额外画一层结算画面"，底下的敌人会**继续开火、继续把地图打烂**，你按 `R` 之前分数还在涨。

解决：把主循环的**更新段整段包起来**：

```python
    # 更新位置（只在进行中；结算画面里世界冻结）
    if game_state == "playing":
        first_pressed_key = tank.pressed_order[0] if tank.pressed_order else None
        tank.move(KEY_TO_DIR.get(first_pressed_key))
        tank.check_collision(screen_rect, all_tanks)
        tank.update_bullets()
        for e in enemies:
            e.maybe_turn(game_ticks)
            e.move(e.direction)
            e.check_collision(screen_rect, all_tanks)
            e.shoot(game_ticks)
            e.update_bullets()
        handle_hits()
        check_game_over()      # ← 放在最末尾（见下）
```

**为什么要包住"玩家移动"**：结算画面里按方向键，坦克还能开——看起来是"死了还能动"的 bug。包进 `if` 就一起解决了。

**为什么 `check_game_over()` 放在这段的最末尾**：让"这一帧完整地打完"再判结束。如果放在 `handle_hits()` 前面，会出现"敌人已经被打光、但这一帧敌人还动了/开了枪"的瞬间；放最后则画面停在"敌人刚好消失"的那一刻。

**绘制段不用包**，因为战场要定格显示：

```python
    draw_map(screen)
    tank.draw(screen)
    for e in enemies:
        e.draw(screen)
        e.draw_bullet(screen)
    tank.draw_bullet(screen)
    draw_hud(screen)
    if game_state == "over":
        draw_result(screen)          # ← 结算画面压在最上层
```

### 3.6 结算判据：两个结束条件

```python
def check_game_over():
    """检查本局是否结束；结束则把状态切成 over"""
    global game_state, result_title, result_sub
    if lives <= 0:
        game_state = "over"
        result_title = "游戏结束"
        result_sub = "生命耗尽"
        return "lose"
    if not enemies:
        game_state = "over"
        result_title = "胜利！"
        result_sub = "敌人已全部消灭"
        return "win"
    return None
```

三个细节：

- **`lives <= 0` 用 `<=` 不用 `==`**：万一一帧里挨了两发、`lives` 从 1 掉到 −1，`== 0` 就漏判了。实测 `lives=-1` 也能正确判定。
- **先判生命、后判敌人**：万一同归于尽（玩家最后一发打掉最后一个敌人，同时被对方的子弹打死），`<= 0` 写在前面就判"游戏结束"。先死不算赢 —— 这样更合理。
- **`global` 必须写**：这里给三个全局变量都赋了值。

### 3.7 ⚠️ 重开时的"三发齐射"坑

`reset_game()` 重建三辆敌人时，它们是**全新对象**，`__init__` 里 `last_shoot = 0`。而你不会在第 0 毫秒重开 —— 假设已经玩了 60 秒：

```python
# 敌人开火判据（main.py:252）：if ticks - self.last_shoot >= self.next_shoot
ticks = 60000, last_shoot = 0, next_shoot = 1000
→ 60000 - 0 >= 1000  →  True   →  立刻开火
```

三辆同时满足 ⇒ **重开后的第一帧，三发子弹齐射**，玩家还没反应过来就被围殴。实测：

```
[PASS] B1 [坑] 不修正 last_shoot -> 重建后第一帧就 3 发齐射  now=60000ms 时会开火 3/3 辆
[PASS] B2 修正 last_shoot 后不再齐射  会开火 0/3 辆
[PASS] B3 修正 last_turn 后也不会立刻换向  会换向 0/3 辆
```

**修法**（`reset_game` 的最后两行）：

```python
    now = pygame.time.get_ticks()
    for e in enemies:      # 冷却从现在算起，避免一重开就三发齐射
        e.last_shoot = now
        e.last_turn = now
```

`last_turn` 同理：不修的话三辆敌人第一帧就集体换向（`2000 - 0 >= 1000`），看起来像"抽风"。

> 用 `pygame.time.get_ticks()` 拿"现在"（和主循环里 `game_ticks` 同一个时基），**不要写死 0** —— 写 0 等于告诉敌人"你上一发是开天辟地时打的"，冷却立刻满足。

### 3.8 `reset_game()` 全貌

```python
def reset_game():
    """重开一局：地图、坦克、敌人、分数、生命全部回到初始状态"""
    global tank, enemies, score, lives, game_state, result_title, result_sub
    score = 0
    lives = 3
    game_state = "playing"
    result_title = ""
    result_sub = ""
    MAP_DATA[:] = [row[:] for row in MAP_BACKUP]   # 切片赋值：原地改，不需要 global
    tank = Tank(360, 280)
    enemies = [Enemy_Tank(40, 40), Enemy_Tank(720, 40), Enemy_Tank(40, 520)]
    now = pygame.time.get_ticks()
    for e in enemies:
        e.last_shoot = now
        e.last_turn = now
```

**为什么 `tank` 要新建而不是"挪回出生点"**：旧坦克身上挂着 `bullets` 列表（上一局的子弹还在飞）、`pressed_order`（上一局按住的键，重开后坦克会自己往前走）、`last_shoot`。新建一辆 = **这四样一起归零**，比逐个清理可靠。实测：

```
[PASS] D3 重开后是新坦克对象（不是把旧坦克挪回去）
[PASS] D9 玩家子弹已清空
[PASS] E1 旧坦克留着按住的键，新坦克的 pressed_order 是独立空列表
[PASS] E3 重开后玩家不会「自动往前走」
```

**`enemies = [...]` 重新赋值而不是 `enemies.clear()` + `append`**：敌人列表里的敌人都带着 `bullets`，重新建列表最干净。

### 3.9 按 `R` 重开的接线（事件处理）

```python
        elif event.type == pygame.KEYDOWN:  # 检测按下按键事件
            # 结算画面按 R 重开一局
            if event.key == pygame.K_r and game_state == "over":
                reset_game()
                continue
            if event.key in DIR_KEYS:
                ...
```

**两个要点**：

1. **必须带 `game_state == "over"` 条件** —— 否则游戏进行中按 `R` 会突然清空重来（`R` 键就在 `W` 旁边，容易误触）。
2. **`continue`** —— 让这次按键到此为止，不要再往下走去判断方向键/空格。少了它有啥后果？`pygame.K_r` 不在 `DIR_KEYS` 里、也不是 `K_SPACE`，所以**不会真出 bug**；但加上它语义更清楚，也防止以后往后面加别的 `elif` 时意外命中。

## 6. 踩过就懂的坑

1. **`MAP_BACKUP = MAP_DATA`（直接赋值）** → 只是起别名，存档和地图是同一个列表，打掉的墙"存"了个寂寞。**必须 `[row[:] for row in MAP_DATA]`**（3.2）。
2. **`MAP_BACKUP = [row for row in MAP_DATA]`（只拷外层）** → 行对象还是共享的，存档会跟着地图一起被改。这是本条最阴的一坑，**看着像拷贝，其实不是**。
3. **恢复时写 `MAP_DATA = [...]`（重新赋值）** → 别处缓存的引用还指着旧列表。**用切片赋值 `MAP_DATA[:] = ...`**（3.2）。
4. **`reset_game` 里漏写 `global`** → 函数跑完什么都不变，**且不报错**。最坑的变体是"先读后写"：`lives = lives - 3` 类的写法会直接抛 `UnboundLocalError: cannot access local variable`。
5. **以为 `MAP_DATA[:] = ...` 也需要 `global`** → 不需要（3.3）。但**别因此以为整个函数都不用写** —— 其余 7 个变量都要。
6. **`OVERLAY` 放在 `pygame.display.set_mode()` 之前创建** → `error: No convert format has been set, try display.set_mode()`. 顺序必须是 `set_mode` → 建 Surface → `set_alpha`。
7. **忘了给遮罩 `set_alpha`** → 整屏纯黑，战场完全看不见（想确认的话把 170 调成 100 试试）。
8. **遮罩每帧贴多次** → 越贴越黑（实测连贴 4 次后颜色只剩 15/255）。正常写法不会踩，写淡入动画时会。
9. **更新段没包进 `if game_state == "playing"`** → 结算画面里敌人继续开火、分数继续涨、地图继续被打烂，玩家按 `R` 之前世界还在跑。
10. **只包了敌人生成/移动、没包玩家的 `tank.move`** → "死了还能开坦克"。
11. **重开时敌人没修正 `last_shoot`** → 第一帧三发齐射（3.7）。**这是本条最容易被忽略、也最影响体验的坑。**
12. **重开时没重建 `tank`** → 上一局的子弹还在飞、上一局按住的键还在 `pressed_order` 里，新局坦克自己往前走。
13. **`lives <= 0` 写成 `lives == 0`** → 一帧挨两发时 `lives` 从 1 跳到 −1，判据漏掉，游戏卡在"死了但不结算"。
14. **先判敌人清空、后判生命** → 同归于尽时判成"胜利"。**生命判据写前面**。
15. **按 `R` 的条件只写 `event.key == pygame.K_r`** → 玩的时候误触 `R`（就在 `W` 旁边）直接清空重来，**必须带 `game_state == "over"`**。
16. **`check_game_over()` 放在更新段最前面** → 出现"敌人已消失但还动了一下"的瞬间。**放最后**（3.5）。
17. **把 `running` 当游戏状态复用** → `running = False` 会让主循环整个退出、程序关掉，而你要的是"这一局结束"。**两个变量，各管各的**。
18. **忘了删/改条目 12 遗留的 `last_score, last_lives = score, lives`** → 那行随 `print` 段一起成了死代码，本条顺手删掉（它在主循环里每帧跑一次，无害但碍眼）。
