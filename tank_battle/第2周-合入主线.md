## 3. 核心概念：合并的三种结果

| 情况 | Git 做什么 | 图上长什么样 |
|---|---|---|
| **快进（fast-forward）** | `dev` 是对方的祖先 ⇒ 直接把 `dev` 指针挪过去 | 一条直线，**没有**合并点 |
| **三方合并** | 两边各有对方没有的提交 ⇒ 造一个**合并提交**（两个 parent） | 出现 `\` `/` 分叉 + `Merge branch ...` |
| **冲突（conflict）** | 两边改了**同一处**，Git 不敢替你决定 ⇒ 停下来交给你 | 合并停在中途，文件里出现 `<<<<<<<` |

要点：

- **要出合并点，就得让两边都往前走**；历史分叉了，合并才是"真合并"。
- **要出冲突，就得让两边改到同一行**。真实项目里这很常见（两个人改同一个文件、同一份文档的同一段）。
- **`--no-ff`**：即使能快进，也强行造一个合并提交。作用是把"这里合进过一个功能分支"这个事实留在历史里（团队常用）。本例历史已经分叉，不加 `--no-ff` 也是真合并 —— 但你要知道有这个东西。
- **合并只负责"保住两边的改动"，不负责"谁写得对"**。冲突怎么解是你的决定，Git 只把两种改法摆在你面前。

### 第 3 步 · 回 `dev` 合并 → 撞上冲突

```powershell

```

**必然**输出（实测原文）：

```

```

> `--no-edit` 是**必须加的**：不加的话 Git 会拉起编辑器让你确认合并信息。2026-10-13 那次事故就出在这里，见第 7 节第 1 条。

### 第 4 步 · 看懂冲突现场

```powershell

```

你会看到（实测原文，注意其中**两件事**）：

```

  (use "git add <file>..." to mark resolution)
	both modified:   tank_battle/坦克大战复健项目 —— 目标与需求说明.md   ← ② 只有这一个文件要你处理
```

① 说明**代码部分 Git 自动合好了** —— `main.py` 的改动来自 `c248dfb`，已经在暂存区，**你什么都不用做**；
② 说明只有一个文档文件需要你手工决定。

打开那个 md，冲突处长这样（实测原文）：

```
<<<<<<< HEAD
| 2026-10-14 | v0.3 | 条目 8 碰撞检测完成：子弹可打掉砖墙、被钢墙挡住，坦克撞墙走不动 |
=======
| 2026-10-14 | v0.3 | 碰撞检测：坦克撞墙回退、子弹打砖墙 |
>>>>>>> feature/collision
```

怎么读它：

- `<<<<<<< HEAD` 到 `=======` 之间 = **你当前所在分支（`dev`）**的版本
- `=======` 到 `>>>>>>> feature/collision` 之间 = **要被合进来的分支**的版本
- **三行标志（`<<<<<<<`、`=======`、`>>>>>>>`）必须全部删掉**

### 第 5 步 · 手工合并（这一步是人的决定）

留哪一行、还是两行都留，**由你决定** —— 这就是"解决冲突"的全部含义。本例建议**合成一行**，把两条信息都保住：

```
| 2026-10-14 | v0.3 | 条目 8 碰撞检测完成：坦克撞墙回退、子弹打砖墙、被钢墙挡住（探针 48 项全过） |
```

改完后，文件里**再没有任何** `<<<<<<<` / `=======` / `>>>>>>>`。

## 7. 常见坑（按踩中概率排序）

1. **⚠️ 合并时忘加 `--no-edit` → 弹出编辑器，你以为卡住了。** 这就是 2026-10-13 那次事故的现场：终端停在一个你没认出来的编辑器里等确认，人却转头在 **VS Code 源代码管理面板**点了提交 → 两个进程同时收尾 → 合并提交做出来了，但 `.git\MERGE_HEAD` 被撕成 **0 字节**（正常 41 字节），`git status` 说 `All conflicts fixed but you are still merging`，`git rev-parse MERGE_HEAD` 却说 `Needed a single revision`。**规矩：合并一律 `--no-edit`，并且合并进行中不要碰源代码管理面板。**（本机 `git var GIT_EDITOR` 现在已是 `code --wait`，当时已根治。）
2. **⚠️ 冲突期间在源代码管理面板给冲突文件点 `+` = 宣告「这冲突我解决好了」。** 面板不管文件里还有没有 `<<<<<<<`，你一点，Git 就认定冲突已解决、于是放行 `git commit`。**2026-10-14 真实踩中**：终端 `git merge feature/collision --no-edit` 报冲突后，文件一个字没改，只在面板上给那个 md 点了 `+`，接着终端 `git commit --no-edit` 顺利通过 —— **三行冲突标记被原样提交进 `abba6c9` 并 push 到了 GitHub**（`git commit` 本该在冲突未解决时拒绝你，是那个 `+` 让它放行了），最后只能再补一个 `a992c4c fix: 清除误带入合并提交的冲突标记` 收场。**规矩：冲突期间只改编辑器里的文件、只在终端 `git add` 那一两个文件；面板只用来"看状态"，不点 `+`、不点提交。**
3. **⚠️ 那种"撕裂状态"下的两条禁忌**：**别 `git commit`**（会真的多造一个空提交）、**别 `git merge --abort`**（它的设计是回退到 `ORIG_HEAD` = 合并**前**，会把刚做出来的合并提交整个丢掉）。正确命令是 **`git merge --quit`**（保留已提交的合并，只清掉合并登记）。
4. **分清两种"退出合并"**：
   - 合并**还没提交**（正常冲突现场，`git status` 会正常列出 `Unmerged paths`）→ 想放弃就 `git merge --abort`，**这时它是对的**；
   - 合并**已经提交**、只是登记没清干净 → 用 `git merge --quit`。
   - 判断依据：`git rev-parse MERGE_HEAD` **能不能给出哈希**。
5. **忘了删冲突标记就提交** → 文件里留着 `<<<<<<<`，文档全是坏的（第 2 条就是活案例）。提交后扫一遍第 5 节第 4 条那条命令。
6. **在 `main` 上合并** → 本轮目标是 `dev`。敲 merge 之前先 `git branch --show-current` 看一眼。
7. **`git add .` 顺手把不该提交的东西带进去** → 本例只改了 1 个 md，**按文件名 add**。（`__pycache__`、`.vscode` 都已被 `.gitignore` 盖住，但习惯要养。）
8. **合并前工作区不干净** → Git 会直接拒绝（`Your local changes would be overwritten`）。动手前 `git status` 必须是干净的。
9. **`git pull` 报错就慌** → 本轮两边都与远端一致，`pull` 只会打印 `Already up to date.`；网络不好跳过它，不影响本条。
10. **看到 `warning: LF will be replaced by CRLF` 不用慌** → 这是换行符自动转换提示（`core.autocrlf=true`），不是错误，内容不受影响。
11. **push 被拒（`rejected ... non-fast-forward`）** → 说明远端 `dev` 上有你本地没有的提交。**别 `--force`**（`dev` 是共享分支）：先 `git pull`，看懂再推。
