## 2. 先想清楚三个设计问题（想完再动手，比写错再改快）

### 2.1 屏幕坐标系（最容易搞反的地方）

```
(0,0) ──────────► x 增大（向右）
  │
  │
  ▼
 y 增大（向下）
```

所以「**向上**移动」= y **减小**，写 `-speed`。如果你发现按上键坦克往下跑，就是这里反了。

### 2.2 方向用什么表示？（自己选，并说出理由）

| 候选 | 好处 | 代价 |
|---|---|---|
| 字符串 `"up"` / `"down"` / … | 打印调试一眼看懂；条目 4 画炮管时写 `if direction == "up"` 很直观 | 想按方向算位移时要写 `if/elif` |
| 元组 `(0, -1)` / `(0, 1)` / … | `rect.move(*direction)` 一行搞定位移 | 调试时打印 `(0, -1)` 要想一下 |
| `pygame.Vector2` | 能算角度，条目 4 画炮管方便 | 对现阶段偏重 |

**没有标准答案**，选一个你讲得出理由的。条目 4（画炮管）会让这个选择显出差别。

### 2.3 位置存在哪？

推荐**只存一个 `pygame.Rect`**（比如 `self.rect`）。理由：
- 以后**碰撞检测**（条目 8）用的就是 `Rect.colliderect`，位置和碰撞盒天然同源；
- 边界限制有内建方法（见 API 表），不用手算；
- 避免 `self.x` 和 `self.rect.x` **两个数据源不同步**的经典 bug（改了 x 忘了 rect）。

### 2.4 「读键盘」和「改位置」放一个方法还是两个？

两种都行：`handle_input(keys)` 里一起做，或 `handle_input` 只记方向、`update()` 负责移动。
后者在条目 6（子弹）之后会更好用。**现在是练手，选简单的即可**，但要知道为什么以后可能要拆。

## 3. 你要用到的 API（自己组织，本文不给成品代码）

| API | 干什么 | 关键点 |
|---|---|---|
| `pygame.key.get_pressed()` | 返回**当前所有按键**的按下状态（序列），用 `keys[pygame.K_LEFT]` 取布尔值 | ⚠️ **必须在 `pygame.event.get()` 之后调用**（键盘状态靠事件泵更新）；适合「按住持续移动」 |
| `pygame.event.get()` + `KEYDOWN` | 单个键「按下的那一瞬间」的事件 | 适合发射子弹、切菜单这类**单次触发**；**别用它写移动**（会变成一下一下点） |
| `pygame.K_UP` / `K_DOWN` / `K_LEFT` / `K_RIGHT` | 方向键键码 | 也可加 `K_w/K_a/K_s/K_d` 作为第二套键位 |
| `pygame.Rect(x, y, w, h)` | 矩形对象（位置 + 碰撞盒） | 属性 `x/y/top/bottom/left/right/centerx/centery`；**改任何一个都会同步其他** —— 这正是用它当唯一数据源的好处 |
| `rect.move(dx, dy)` | 返回**新的** Rect（原对象不变） | 容易忘「返回新对象、不会改动自己」 |
| `rect.clamp_ip(other)` | **原地**把矩形夹进另一个矩形内 | 一行实现边界限制；`screen.get_rect()` 就是整个窗口 |
| `pygame.draw.rect(screen, color, rect)` | 画一个填充矩形 | 条目 3 先用它做「占位坦克」；条目 4 再拼车体 + 炮管 |
| `screen.get_rect()` / `get_width()` | 拿窗口矩形 / 宽高 | **别硬编码 800 / 600**，以后改窗口尺寸不用改代码 |

## 4. 建议的实现顺序（每小步都留一个能跑的状态）

1. **先画个静止方块**：在现有循环里加一行 `pygame.draw.rect(...)`，画在屏幕中央（约 `x=380, y=280`，尺寸 40×40）。
   跑一下 —— 看到方块就说明坐标系对了（**顺手改几个数字，看它往哪边挪**，这比读文档管用）。
2. **抽出 `Tank` 类**：`__init__(self, x, y)` 里建 `self.rect`、`self.direction`、`self.speed`；
   把刚才那行画方块搬进 `draw(self, screen)`；主循环里 `tank = Tank(380, 280)` + `tank.draw(screen)`。
   **这一步行为必须和第 1 步一模一样** —— 这叫重构：只搬代码、不改行为。改完先跑一遍确认没变。
3. **加输入与移动**：循环里 `keys = pygame.key.get_pressed()`（放在 `event.get()` 之后）→
   `tank.handle_input(keys)`：四个方向各一个 `if`，**既改 `direction` 也改位置**。
4. **加边界限制**：`self.rect.clamp_ip(screen.get_rect())`，或逐边判断（`if self.rect.left < 0: …`）。
   注意顺序：**先移动、再夹取**。
5. **自测**：四方向各走一遍 → 按住不放 → 四个边界各顶一次 → 松手即停。

## 7. 常见坑（按踩中概率排序）

1. **把移动写在 `KEYDOWN` 事件里** → 按住没反应，得一下一下点。移动要用 `key.get_pressed()`（每帧轮询）。
2. **`get_pressed()` 写在 `event.get()` 之前** → 键盘状态不刷新，表现为「按了没反应」或「慢半拍」。**顺序必须是先泵事件、再读键盘。**
3. **`self.x` 和 `self.rect.x` 两个数据源** → 一个更新了另一个没更新，坦克「看得见但撞不着」或「位置跳变」。**只用一个。**
4. **方向搞反**（按上往下走）→ 忘了 y 轴向下为正。
5. **先夹取边界、后移动** → 边界限制等于白写，一帧就窜出去了。**顺序：先 move、再 clamp。**
6. **速度太大**（比如 50）→ 一帧跨半个屏幕，看起来像瞬移；贴近边界时会「闪」。位移动类游戏的 60 FPS 下手感，**3~5 是比较合适的起点**。
7. **忘了每帧 `fill()`** → 屏幕拖出一条运动轨迹（虽然能当调试手段看运动路径，但那是 bug）。
8. **浮点速度**：`self.speed = 3.5` 时 `rect.x` 会被取整（Rect 内部是整数），长时间累积会有 1 像素误差 —— 现在无所谓，条目 15 调手感时再管。
9. **`clamp_ip` 传错参数**：它要的是**一个 Rect**（`screen.get_rect()`），不是宽高数字。
10. **切分支时不干净** → 上个分支的未提交改动被带过来，之后 `git status` 一片红。养成「切分支前先 `git status`」的习惯。
